# Релизы

Версии — [SemVer](https://semver.org/lang/ru/), история — [CHANGELOG.md](../CHANGELOG.md).
Одна версия на весь монорепо: корневой `package.json` и `packages/*/package.json` всегда совпадают.

## Как выходит релиз

Мерж PR в `master` запускает `.github/workflows/release.yml`:

1. Собирает PR, влитые после последнего тега `v*`.
2. Выбирает тип подъёма версии (ниже) и поднимает `version` во всех `package.json`.
3. Переносит раздел `[Unreleased]` из CHANGELOG в `## [X.Y.Z] - дата`. Если раздел пуст,
   пишет туда заголовки PR со ссылками.
4. Коммитит `chore(release): vX.Y.Z [skip ci]`, ставит тег `vX.Y.Z`, публикует GitHub Release
   с текстом раздела.

Деплой (`ci.yml`, [deploy.md](deploy.md)) не меняется: выкатывается мерж-коммит, коммит релиза
CI не запускает.

## Тип подъёма

| Условие                                                    | Подъём      |
| ---------------------------------------------------------- | ----------- |
| метка `release:skip`                                       | без релиза  |
| метка `release:major` / `minor` / `patch`                  | как в метке |
| заголовок `feat: …` / `feat(…): …` или метка `enhancement` | minor       |
| всё остальное                                              | patch       |

Метки важнее заголовка. Если с прошлого релиза влито несколько PR, берётся самый сильный подъём.
`1.0.0` и дальше мажорные версии — только меткой `release:major`.
PR Dependabot помечаются `release:skip`: обновления зависимостей уходят в следующий релиз.

## Что делать в PR

Опишите изменение в `[Unreleased]` по группам «Добавлено», «Изменено», «Исправлено» со ссылкой на
PR. PR, на который в разделе нет ссылки, попадёт в релиз своим заголовком в нужную группу.

## Защита от петель и гонок

- Коммит релиза помечен `[skip ci]`, а джоб пропускает коммиты `chore(release):`.
- Каждый запуск выпускает всё, что накопилось после последнего тега, поэтому отменённый или
  пропущенный запуск догонит следующий.
- Push атомарный (`--atomic`): если `master` успел уйти вперёд, не пушится ни коммит, ни тег;
  релиз выпустит запуск от нового мержа.
- Первый запуск ставит тег текущей версии (`v0.1.0`) на `master` перед мержем, который добавил
  `release.yml`, — от того, какой запуск дошёл первым, это не зависит.
- Последний шаг публикует GitHub Release для каждого тега `v*`, у которого его ещё нет. Упала
  публикация — перезапустите джоб или Actions → Release → Run workflow.

## Настройка

`master` защищён (PR и ревью обязательны), а `GITHUB_TOKEN` такую защиту обойти не может. Поэтому
коммит релиза пушится токеном `RELEASE_TOKEN`:

- fine-grained PAT администратора: Resource owner `BaldPippins`, доступ только к
  `BaldPippins/graveshift`, право `Contents: Read and write`;
- Settings → Secrets and variables → Actions → секрет `RELEASE_TOKEN`.

Без секрета джоб падает с понятной ошибкой, остальной CI это не затрагивает. У токена есть срок
жизни: когда истечёт, выпустите новый и обновите секрет.

## Бейджи

`.github/workflows/badges.yml` на каждый push в `master` запускает `pnpm coverage`
(`@vitest/coverage-v8`) и кладёт `coverage.json` и `tests.json` в формате
[shields.io endpoint](https://shields.io/badges/endpoint-badge) в ветку `badges` (один коммит,
перезаписывается). README берёт их оттуда через `raw.githubusercontent.com`.

Локально: `pnpm coverage` печатает сводку покрытия.
