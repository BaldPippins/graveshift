# Сериализация обновлений общего JSON между слотами

## Context

Два слота blue-green используют общий файл доступности карт. Замена SQLite на JSON требует
сохранить настройки при конкурентных действиях администраторов и не отключить последнюю карту.
Переход на JSON с блокировкой всей операции был согласован при разборе PR #16 (session history).

## Guidance

Разделяйте две гарантии. Временный файл и атомарный `rename` дают читателям целую версию JSON.
Межпроцессная блокировка охватывает всю операцию: повторное чтение актуального файла в обход кеша,
проверку допустимости изменения и атомарную запись. Проверять инвариант до получения блокировки
недостаточно, даже если сама запись атомарна.

В `packages/server/src/infrastructure/admin/AdminSettingsStore.ts` запись повторно читает
настройки через `read(true)` внутри `withAdminSettingsLock`. Реализация блокировки и замены файла
находится в `packages/server/src/infrastructure/admin/adminSettingsFile.ts`. Занятую или
повреждённую блокировку автоматически не снимают; порядок восстановления описан в
[инструкции развёртывания](../../deploy.md).

## Why This Matters

Атомарное переименование исключает частично записанный JSON, но не проверяет, что решение об
изменении принималось по последней версии. Два процесса могут прочитать одинаковое состояние,
каждый успешно записать свою версию и потерять изменение другого. Блокировка вокруг повторного
чтения и проверки превращает обновление в одну последовательную операцию для обоих слотов.

## When to Apply

- Общий файл используют несколько процессов, например во время blue-green деплоя.
- Запись основана на старом значении или должна соблюдать ограничение, зависящее от других записей.
- Замена файла целиком уже атомарна, но требуется также защитить состояние от потерянных изменений.

## Examples

При двух включённых картах запросы на отключение каждой из них могут стартовать одновременно.
Без общей блокировки оба способны проверить исходный снимок и сообщить об успехе, хотя последняя
запись затрёт результат первой. Под блокировкой второй процесс либо получает отказ из-за занятого
lock-файла, либо после повторного чтения видит одну оставшуюся карту и отклоняет её отключение.

Регрессионный тест в `packages/server/src/infrastructure/admin/AdminSettingsStore.test.ts`
запускает два отдельных процесса и проверяет, что успешно отключена только одна карта. Отдельные
проверки покрывают повреждённый lock-файл, повторное открытие настроек и перенос прежней базы.
