# Сериализация обновлений общего JSON между слотами

## Context

Два слота blue-green используют общий файл доступности карт. В PR #16 принято условие:
настройки меняет один администратор последовательно, без конкурентных записей.

## Guidance

Разделяйте две гарантии. Временный файл и атомарный `rename` дают читателям целую версию JSON.
Если записи могут выполняться одновременно, для сохранения всех изменений нужна сериализация всей
операции: повторного чтения, проверки и записи. Атомарной замены самого файла для этого недостаточно.

В `packages/server/src/infrastructure/admin/AdminSettingsStore.ts` запись повторно читает
настройки через `read(true)`, проверяет наличие включённой карты и атомарно заменяет файл с помощью
`packages/server/src/infrastructure/admin/adminSettingsFile.ts`. Межпроцессной блокировки нет:
система полагается на последовательное администрирование, как описано в
[инструкции развёртывания](../../deploy.md).

## Why This Matters

Атомарное переименование исключает частично записанный JSON, но не проверяет, что решение об
изменении принималось по последней версии. Два процесса могут прочитать одинаковое состояние,
каждый успешно записать свою версию и потерять изменение другого. Если требование единственного
последовательного администратора изменится, эту гонку нужно устранить отдельным механизмом.

## When to Apply

- Общий файл используют несколько процессов, например во время blue-green деплоя.
- Запись основана на старом значении или должна соблюдать ограничение, зависящее от других записей.
- Замена файла целиком уже атомарна, но требуется также защитить состояние от потерянных изменений.

## Examples

При двух включённых картах запросы на отключение каждой из них могут стартовать одновременно.
Без общей сериализации оба способны проверить исходный снимок и сообщить об успехе, хотя последняя
запись затрёт результат первой. При последовательных запросах второй процесс повторно читает файл,
видит одну оставшуюся карту и отклоняет её отключение.

Регрессионный тест в `packages/server/src/infrastructure/admin/AdminSettingsStore.test.ts`
проверяет последовательные изменения из разных экземпляров, повторное открытие настроек,
устаревший lock-файл и сохранение повреждённого JSON без перезаписи.
